34.1. Index cleanup → remove indexes that provide little to no benefit                                                                                                                     -->faster writes/loads, less storage and maintenance
→ Unused: no reads but many writes | Duplicate: two indexes with the same keys → remove one | Overlapping: Like (CustomerID) and (CustomerID, OrderDate) → review whether both are needed or one
→ When to use Index Cleanup: INSERT/UPDATE/DELETE or ETL loads are slow; too many indexes exist; periodic maintenance
→ Remember:--- check a full business cycle(History). an index might serve only monthly reports; make sure dont delte primary key
34.2. Fragmentation → index pages become scattered or partly empty (like book pages out of order with unused space)                                       --> can make large index scans/range filters less efficient
→ Cause: INSERT/UPDATE can split pages; UPDATE/DELETE can leave empty space
→ Traditional guide: <5% → leave | 5–30% → consider REORGANIZE (reorder/compact pages) | >30% → consider REBUILD (recreate index) → percentages alone don’t prove maintenance is needed
→ Effect of fixing: better page organization/density → potentially fewer reads and faster scans; improvement depends on the workload.
34.3. Statistics → SQL Server’s summary of data distribution → estimates how many rows match a condition                                                        → **Example:** expects 10 rows, receives 100,000 → a plan chosen for a small result may perform poorly  
→ **When to check:** after large ETL loads/major data changes; slow queries with large differences between estimated and actual rows  
→ **Update effect:** fresh distribution information → better row estimates → potentially better execution plans  
→ **Remember:** auto-update usually handles routine changes; wrong estimates don’t always mean statistics are outdated.

35. Partitioning:-  split one very big table into smaller by a column (usually date) → you still query ONE table, but SQL reads only the piece it needs → faster queries.   Example → sales table with 100M rows (2020 to 2023) → split by year → each year is its own partition → query for 2022 reads only the 2022 partition, skips the other 75M rows          -->Like a cupboard with one drawer per year → need 2022 → open only that drawer          CREATE PARTITION FUNCTION Sale (DATE)  AS RANGE RIGHT FOR VALUES ('2021-01-01', '2022-01-01', '2023-01-01');
   
36. Performance Tips:
1..Select  
-->Select only the columns you need, not * → less data read and sent    
-->Exploring a table → SELECT TOP 5 * | latest rows → SELECT TOP 5 * ... ORDER BY date DESC    
-->Avoid unnecessary ORDER BY and DISTINCT → both force a sort, very costly on big tables
2..Filter (WHERE)
-->use filter or non clusterd index on most frequntly used one like. order = shiped
-->WHERE YEAR(order_date) = 2026 ❌ → WHERE order_date >= '2026-01-01' AND order_date < '2027-01-01' ✅
-->WHERE LOWER(name) = 'ali' ❌ → WHERE name = 'ali' ✅ (SQL Server is case insensitive by default, LOWER not needed)
-->Prefer >= and < over BETWEEN for dates → BETWEEN misses rows with a time part on the last day
Join & Union
--> where status = shiped   insted   on c.id = s.id and c.status = shiped    or forbig table use left join(select * from sale where status = shiped) s on c.id = s.id
-->UNION ALL → fast, no duplicate check | UNION → removes duplicates → extra sort
Aggregation / Big queries
-->Heavy aggregation on huge fact table → Columnstore index
-->Slow complex query → break into steps → SELECT ... INTO #temp → query the temp table (CTAS / INTO)
-->Partition very large tables (by year / month) → SQL reads only the needed partition
Table design
-->VARCHAR(50), not plain VARCHAR → plain VARCHAR = VARCHAR(1) in DECLARE → silently cuts your data
-->Right size types → don't use NVARCHAR(MAX) for a name, use NVARCHAR only if you need Unicode (Arabic, Urdu)
-->NOT NULL where data is always required → cleaner data, optimizer works better
Indexing
-->Avoid over indexing → every index slows INSERT / UPDATE / DELETE
-->Drop unused (Monthly.sql) | update statistics weekly + after every big load
-->Never drop PK, clustered, or unique indexes → save the CREATE script before any DROP
